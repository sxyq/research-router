# 场景路由

先判断“要解决什么问题”，再判断需要多少子代理。三类场景可以共享平台 Skill，但证据目标不同。

## `bug-fix`

输入通常包含报错、异常行为、版本、运行环境或代码位置。优先查询错误原文、库名/版本、相关 API、Issue、提交和测试。若用户给出仓库或要求解释实现，加入 `github-analyze`。

## `open-source`

目标是发现、比较或评估开源项目、Skill、插件和工具。先按用户目标、候选能力、生态范围和评价条件做语义匹配，再让 GitHub 适配器生成查询表达。GitHub 结果先发现，再验证 README、目录和源码。

## `academic`

目标是发现论文、作者、会议、研究方向或证据。先做论文发现和元数据核对；需要论断支持时，再读取论文正文或 PDF，并将论断映射到短引文。

论文候选产生后，若任务要求正文引文、PDF、本地文献文件或证据表，Router 追加内部 `academic-evidence`。该模块只负责发现之后的证据处理，不参与第一阶段的论文搜索。

## 平台判断

- 用户明确点名平台时，优先使用该平台的注册项。
- 用户没有点名平台时，先使用已验证的综合 Skill 做轻量发现，再根据需求缺口增加专项 Skill。
- “中国抖音”与 TikTok 分开处理。
- GitHub 和论文的深层证据要求会自动提高该平台的最低深度，但不会强行扩大其他平台。
