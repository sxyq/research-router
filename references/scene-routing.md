# 场景路由

Agent 先理解主要研究目标，再判断“查多深”。四类场景可以共享平台 Skill，但证据目标不同。Scene 是主策略，不是关键词分类器；混合请求保留其他证据需求。

## `bug-fix`

输入通常包含报错、异常行为、版本、运行环境或代码位置。优先查询错误原文、库名/版本、相关 API、Issue、提交和测试。若用户给出仓库或要求解释实现，使用仓库内置 GitHub adapter 获取仓库与源文件，再由 Agent 分析。

## `open-source`

目标是发现、比较或评估开源项目、Skill、插件和工具。查询词必须同时表达用户要解决的问题、候选能力、生态名称和评价/维护条件。GitHub 结果先发现，再验证 README、目录和源码。

## `academic`

目标是发现论文、作者、会议、研究方向或证据。先做论文发现和元数据核对；需要论断支持时，再读取论文正文或 PDF，并将论断映射到短引文。

## `community`

目标是发现公开论坛中的讨论、实践报告、问题处理经验和工具使用反馈。论坛正文是经验材料，不能直接替代官方文档、源码或实验结果。

## 判断边界

例如“找一个开源项目解决这个报错，并比较哪个项目维护最好”，主目标可能是开源方案选择，Scene 可以是 `open-source`；报错、Issue 和维护情况仍分别进入 requirement 与 evidence。不要因为命中一个词就覆盖主目标。

## 平台判断

- 用户明确点名平台时，优先使用该平台的注册项。
- 用户没有点名平台时，先使用仓库内置公开发现脚本，再根据证据缺口选择本地适配器；已有外部专项 Skill 只作可选增强。
- “中国抖音”与 TikTok 分开处理。
- GitHub 和论文的深层证据要求会自动提高该平台的最低深度，但不会强行扩大其他平台。
- 52pojie、吾爱破解和吾爱社区归入 `community`；GitHub 仍是源码和项目实现的一类平台，52pojie 是二类社区来源。
