# 需求驱动的查询表达

查询表达服务于已经完成的语义路由。Router 先判断用户要解决的问题和证据标准，再由最终平台 Skill 把需求转换成站内搜索字段、过滤条件或网页搜索表达。关键词不能单独决定平台、Skill 或查询深度。

## 语义匹配模型

先提取以下信息，并与注册表中的平台能力、Skill 职责和边界逐项匹配：

- 目标：用户要发现、比较、解决、验证或提取什么。
- 对象：项目、报错、论文、帖子、作者、趋势或实现细节。
- 领域：语言、框架、系统、AI、部署、学术方向等。
- 约束：平台、语言、时间、登录要求、许可证和输出格式。
- 证据：摘要、原帖、源码、Issue、PDF 正文、评论或交叉来源。
- 终点：需要停在搜索结果、主题详情、回复、源码分析或证据表的哪一层。

匹配结果应说明“为什么这个平台和 Skill 能完成目标”，而不是只说明“它包含某个关键词”。

## 适配器输入生成顺序

1. 写出目标句和证据终点。
2. 完成平台与 Skill 的语义匹配。
3. 根据已选适配器的字段生成站内查询表达。
4. 加入必要的时间、版本、分类、标签、作者或 `site:` 限定。
5. 保留能改变结果集合的表达，去掉随机同义词堆叠。

## 三类查询模板

### 开源项目或 Skill

- `<问题目标> + agent skill`
- `<能力组合> + multi-platform + skill`
- `<平台集合> + search adapter + agent`
- `<目标工具> + README + source code + tests`
- `<目标工具> + alternatives + maintenance + community`

### 修 Bug

- `<完整错误文本> + <库/版本>`
- `<错误现象> + <API/框架> + fix`
- `<仓库> + issue + <错误文本>`
- `<仓库> + commit + regression test`

### 论文

- `<研究问题> + survey + benchmark`
- `<方法/任务> + recent papers + venue`
- `<论断> + primary paper + full text`
- `<方法> + ablation + reproducibility`

## GitHub 查询要求

GitHub 项目发现可用 3–5 组互补查询；候选确认后再读取 README、树、依赖、入口源码、测试、Issue 和 Release。标题命中不等于需求命中。
